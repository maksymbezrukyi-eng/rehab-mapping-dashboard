## Структура проєкту

```
app.py                          — весь застосунок (single-file)
requirements.txt                — Python-залежності
NEW_Mapping_tracker_2506.xlsx   — вихідні дані по закладах (аркуш "Provider Data")
ukraine_hromadas.geojson        — межі 1472 територіальних громад України
.gitignore
```

## Встановлення та запуск

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r requirements.txt
streamlit run app.py
```

Обидва файли даних лежать поряд з `app.py` — шляхи `EXCEL_PATH`/`GEOJSON_PATH` обчислюються відносно `Path(__file__).parent`, тому запуск працює з будь-якої робочої директорії.

## Архітектура ETL-пайплайну

Уся важка обробка даних відбувається в **одній** кешованій точці входу — `prepare_data(excel_path, geojson_path)` (`@st.cache_data`, ключ — лише два рядки шляхів до файлів). Усередині послідовно:

1. **`load_excel_data`** — читає `Provider Data` з `skiprows=3` (не 2 — див. вище про структуру заголовків), відкидає порожні рядки й рядки без `Hromada`, одразу обчислює службові колонки `hromada_norm`, `hromada_norm_baseline`, `_is_medical`, `_ownership_key` (щоб не рахувати їх повторно в кожному фільтрі/агрегації).
2. **`load_geojson`** — вантажить GeoJSON, для кожної фічі одразу рахує `hromada_en`/`oblast_en` (транслітерація), `norm_key` (ключ зіставлення).
3. **`log_mapping_impact`** — друкує в консоль ефект словника винятків "до/після" (діагностика, не впливає на UI).
4. **`geocode_facilities`** — рахує `lat`/`lon` для кожного закладу (центроїд громади + jitter, див. нижче).
5. **`aggregate_providers`** → групує заклади по `hromada_norm` (кількість, медичні/соціальні, розподіл за формою власності, список областей/районів).
6. **`find_unmatched`** — громади з Excel без відповідного полігону в GeoJSON.

**Чому саме так, а не окремими `@st.cache_data`-функціями, викликаними по черзі з `main()`:** якщо передавати важкі об'єкти (`DataFrame` на 5590 рядків, `GeoJSON` на ~4 МБ) як аргументи в окремо кешовані функції, Streamlit змушений на **кожен** `st.rerun()` (зміна мови, фільтра) заново їх хешувати для перевірки кеш-хіта — це коштує майже стільки ж, скільки сам розрахунок. Об'єднання в один виклик з дешевим ключем (рядки шляхів) означає, що на "теплих" rerun'ах `prepare_data` не виконується взагалі. Виміряний ефект: ~7–15 с (холодний старт) → **~56 мс** (теплий rerun).

## Зіставлення Excel ↔ GeoJSON

Найскладніша частина пайплайну: `Hromada` в Excel і `hromada` в GeoJSON записані **різними мовами** — Excel латиницею (`"Cherkasy Miska Hromada"`), GeoJSON кирилицею (`"Черкаська міська громада"`).

### Крок 1 — нормалізація (`normalize_text` / `normalize_text_en`)

Нижній регістр → видалення апострофів усіх варіантів (`'`, `’`, `ʼ`, `′`) → видалення суфіксних слів (`terytorialna`, `miska`, `silska`, `selyshchna`, `hromada`, `m.`, `s.`, `smt`) → згортання пробілів.

### Крок 2 — транслітерація (`transliterate_ua_to_en`)

Власна реалізація офіційної таблиці транслітерації кирилиця → латиниця за **Постановою КМУ №55 (2010)**, включно з позиційними правилами для `є/ї/й/ю/я` (на початку слова `ye/yi/y/yu/ya`, всередині — `ie/i/i/iu/ia`) і диграфом `зг` → `zgh`. Застосовується до `hromada`/`region` з GeoJSON, щоб отримати спільний із Excel латинський простір для зіставлення.

### Крок 3 — словник винятків (`CITY_TO_HROMADA_MAPPING`)

Excel для великих міст іноді записує **іменникову форму назви міста** (`"Kharkiv"`) замість **прикметникової форми назви громади** (`"Харківська"`), і транслітерація тут не допоможе — це різні словоформи. `normalize_hromada_from_excel` спершу нормалізує сире значення, тоді перевіряє його у словнику винятків; якщо є — підміняє на офіційний прикметник, який проганяється через ту саму транслітерацію+нормалізацію, що й GeoJSON.

Кожен запис словника **звірений напряму з `ukraine_hromadas.geojson`**, а не вгаданий (перевірено пошуком по фактичних `region`/`hromada` в GeoJSON). Два задокументовані в коді нюанси:

- **`"Kyiv"` навмисно відсутній у словнику** — Київ у GeoJSON закодований окремим випадком (`region`/`rayon`/`hromada` = просто `"Київ"`, без прикметникової форми), тож сире значення `"Kyiv"` і без словника коректно зматчиться стандартним шляхом. Додавання туди `"Київська"` лише зламало б природний збіг.
- **`"Oleksandriia"` — відома колізія**: після нормалізації (відкидання "міська"/"сільська") дві РІЗНІ громади — Олександрійська міська громада (Кіровоградська обл.) і Олександрійська сільська громада (Рівненська обл.) — отримують однаковий ключ `oleksandriiska`. Обидва полігони покажуть однакові об'єднані цифри.

### Результат

| | Незматчено рядків закладів | % |
|---|---|---|
| Без словника винятків | 1265 з 5590 | 22.6% |
| Зі словником винятків | ~560 з 5590 | **~10.0%** |

Незматчені громади (з розбивкою по `Oblast`/`Raion` для ручної звірки колізій) видно у вкладці **"Сирі дані"** → розгортка "⚠️ Громади з Excel, не зіставлені з картою" → там же кнопка експорту CSV.

## Геокодування закладів

**Без зовнішніх геокодерів** (Nominatim/Google тощо) — свідоме архітектурне рішення: миттєво, без мережевих запитів, без ризику тайм-аутів чи порушення лімітів безкоштовних API.

Координати закладу = **геометричний центроїд полігону його громади** + невеликий **детермінований jitter**-розкид:

- `polygon_ring_centroid` — класична формула зваженого по площі центроїда полігону (shoelace formula), без залежності від `shapely`.
- `geometry_centroid_and_extent` — для `MultiPolygon` рахує area-зважений центроїд по всіх складових полігонах + приблизний розмір bounding box (для масштабування jitter).
- `jitter_point` — випадковий зсув у межах ~12% розміру громади, **seed = індекс рядка в DataFrame**, тому результат детермінований (стабільний між прогонами, а не "танцює" при кожному перерахунку).

Заклади, чия громада не має відповідного полігону (ті самі ~10% незматчених), отримують `lat`/`lon = None` і просто пропускаються при малюванні точок — без винятків.

## Кешування та продуктивність

| Функція | Кешована? | Чому |
|---|---|---|
| `load_excel_data`, `load_geojson` | ✅ `@st.cache_data` | Ключ — рядок шляху, дешево хешується |
| `aggregate_providers`, `log_mapping_impact`, `find_unmatched` | ✅ `@st.cache_data` | Викликаються лише всередині `prepare_data` |
| `prepare_data` | ✅ `@st.cache_data` | **Єдина** точка входу для UI — ключ дешевий (2 рядки шляхів) |
| `compute_hromada_stats` | ❌ навмисно не кешована | Викликається і на повному, і на інтерактивно відфільтрованому (форма власності/НСЗУ) `df` — вхід міняється щовидгету, кешування не дало б користі; групування ~5600 рядків займає одиниці мілісекунд |
| `build_polygon_map`, `build_points_map`, `geocode_facilities` | ❌ навмисно не кешовані | Дешеві/чисті обчислення, що й так виконуються лише в потрібний момент (усередині `prepare_data` або на кожен рендер, де кеш не дав би виграшу) |

Виміряна продуктивність (на реальних даних, 5590 рядків / 1472 громади):

- Холодний старт (`prepare_data`, включно з геокодуванням): ~7–15 с
- Теплий rerun (зміна мови/фільтра, `prepare_data` НЕ виконується): ~56 мс
- `build_polygon_map`: ~110 мс
- `build_points_map` (з `FastMarkerCluster`, ~5000 точок): ~1 с

## Карта: два режими

Перемикач (`st.radio`, над картою у вкладці "Карта громад") між двома незалежними функціями побудови карти — кожен режим будує лише те, що показує:

### 1. Полігони (`build_polygon_map`)
`folium.Choropleth` — заливка громад за загальною кількістю закладів + `GeoJsonTooltip` (назва громади, всього/медичних/соціальних, розподіл за формою власності).

### 2. Точки (`build_points_map`)
Кожен заклад — кольорова точка: 🔵 комунальні/державні, 🟢 приватні, 🟠 ГО/благодійні/донорські, ⚪ не вказано. Popup з назвою, формою власності, адресою, пакетом НСЗУ.

**`folium.plugins.FastMarkerCluster`, а не `MarkerCluster`.** Перший підхід (`MarkerCluster` + окремий `folium.CircleMarker`/`Popup` на кожен із ~5000 закладів) створював ~5000 окремих Python-об'єктів, кожен з яких розгортався в браузері власним набором JS-викликів (`L.circleMarker(...)`, `.bindPopup(...)`, `.addTo(...)`) — це й спричиняло зависання сторінки ще до того, як спрацьовувала кластеризація. `FastMarkerCluster` передає лише компактний масив `[lat, lon, color, popup_html]`, безпечно серіалізований через Jinja `|tojson`, і будує всі маркери **одним спільним JS-колбеком у циклі** (перевірено: рівно 1 виклик `L.circleMarker(` у згенерованому HTML замість ~5000).

Обидва режими використовують спільну `new_base_map()` з `tiles="OpenStreetMap"` — безкоштовний тайл без API-ключа (на відміну від `cartodbpositron`, який показував водяний знак "API key required").

## Фільтри та інтерфейс

Сайдбар (зверху вниз):

1. **Мова** — `uk`/`en`, впливає на весь інтерфейс і всі підписи на карті.
2. **Область** (`st.sidebar.selectbox`) — фільтрує набір громад на карті; каскадно звужує список у пункті 4.
3. **Форма власності** (`st.sidebar.multiselect`) + **Пакет НСЗУ** (`st.sidebar.radio`, Усі/Так/Ні) — фільтрують і полігони (перерахунок статистики "на льоту" через `compute_hromada_stats`), і точки одночасно, через спільний `df_filtered`.
4. **Громада** (`st.sidebar.selectbox`, каскадний від пункту 2) — при виборі показує компактний список закладів у цій громаді (назва, форма власності, пакет НСЗУ), що враховує фільтри з пункту 3.

Вкладки:
- **🗺️ Карта громад** — KPI-картки (всього/медичних/соціальних/громад із даними) + перемикач режиму карти + сама карта.
- **📊 Сирі дані (Таблиця)** — повна таблиця Excel (перекладені заголовки колонок) + розгортка з незматченими громадами й кнопкою експорту CSV.

## Мультимовність (UI_TEXTS)

Весь текст інтерфейсу — у словнику `UI_TEXTS = {"uk": {...}, "en": {...}}`, жодного захардкодженого рядка в `st.*`-викликах. Структура симетрична між мовами (перевірено програмно під час розробки): однакові ключі верхнього рівня, однакові ключі в `ownership_labels` і `columns`. Формат назв колонок таблиці (`ui["columns"]`) використовується для `.rename()` перед `st.dataframe()`.

## Відомі обмеження

- **~10% закладів (560 з 5590) не мають зіставленої громади** — переважно дрібні населені пункти з нетиповим написанням в Excel, не покриті словником винятків. Повний список — у вкладці "Сирі дані" з можливістю експорту в CSV для ручної звірки.
- **Колізія "Oleksandriia"** (див. вище) — дві різні громади ділять один ключ зіставлення.
- **Перейменування громад не відстежуються** — наприклад, Новоград-Волинський → Звягель (2022) може не збігтися, якщо Excel і GeoJSON використовують різні історичні назви.
- **Координати закладів наближені**, а не точні адреси — центроїд громади + jitter, не реальна геолокація будівлі. Якщо знадобиться точність на рівні адреси, слід підключити зовнішній геокодер (Nominatim з дисковим кешем і rate limiting) — свідомо не робили цього через час виконання (~90+ хв на весь датасет) і політику використання безкоштовного API.
- **`FastMarkerCluster` не зберігає посилань на маркери** (задокументована особливість самого плагіна) — методи на кшталт `get_bounds()` для точкового шару недоступні.

## Діагностика та відлагодження

При кожному холодному запуску в консоль (термінал, де запущено `streamlit run`) друкується блок:

```
============================================================
[CITY_TO_HROMADA_MAPPING] Ефект словника винятків
  Усього рядків закладів: 5590
  Незматчено ДО словника:   1265 (22.6%)
  Незматчено ПІСЛЯ словника: 560 (10.0%)
  Довиправлено рядків: 705
============================================================
```

Це діагностика впливу `CITY_TO_HROMADA_MAPPING` (`log_mapping_impact`), кешована — друкується один раз на холодний старт, не на кожен rerun.
